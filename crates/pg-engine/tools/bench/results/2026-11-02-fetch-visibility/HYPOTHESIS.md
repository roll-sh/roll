# Deferred fetch visibility setup: prospective contract

Draft until frame.json exists. No timed attempt has started.

Claim to test: deferring unused Xids/Vis construction until after the live missing/all-visible heap check improves checked end-to-end range query throughput by at least 2%, reduces server CPU per operation, and preserves point-query performance and the dirty-heap fallback. This is a local 200k-row engine comparison, not a PostgreSQL or product claim.

Change: only exec/sizing.rs production code. One fresh model read-lock check per fetched row; no cache, cross-row promise, planner change, or worker-lifecycle change. The non-visible path still constructs a fresh pruning horizon, locates under read lock, and re-locates under write lock when pruning is needed.

Baseline is retained release 5cfc7904, production tree bfaf631, equal to HEAD a39915dc. Candidate must use exactly cargo build -p pg-engine --release --bin roll-engine --example bench --example scan_bench, CARGO_PROFILE_RELEASE_DEBUG=line-tables-only, matching rustc/profile/features/dependency fingerprints. Both changed source files, the patch, binaries, client, Python tools, fixture manifest, regression harness and source acceptance scripts are frozen before launch.

One launch only, no retries, including zero-sample harness failures. Any harness, identity, value, cleanup or declared performance failure rejects this candidate. No rule edits or source changes after the freeze. On rejection restore checked source and baseline executables; retain evidence and seek a different cause before another fix of the same premise.

Order: untimed instrumented monitor correctness, primary, dirty control only if primary passes, then an independent all-visible confirmation only if both pass. Confirmation uses the same 12x20s primary rule and swaps which binary is copied/launched first and assigned port0. This also reverses runner target order and warmup order; measured rounds remain balanced 6/6. It must independently pass every primary gate; do not pool or select between the two blocks. This is one prospective controller launch with mandatory phases, not a retry. Monitor checks identical plans/settings/prepared counters, correct rows, pg_stat_statements calls/rows/workers, transaction AccessShareLock lifetime and absence of parallel workers. Each phase gets independent fixture copies from the same stopped original. Original fixture manifest and logical digest must remain unchanged. Observer starts before engine launch/warmup. Every result operation is fully value checked by unchanged oltp-values-v1 client.

Primary: auto plan mode, range_scan_100 at 8 clients and point_select at 1; 12 measured alternating paired rounds of 20s after round00 warmup. Exact one-sided signed-rank on paired log range throughput ratios p <= .01; Hodges-Lehmann log gain >= log(1.02); median paired range server CPU/op < 1; point throughput >= .98. Pair ordering alternates baseline/candidate first equally. Whole heap all-visible on both sides before and after (all_visible == heap pages > 0).

Dirty fallback: disable autovacuum globally and on accounts in both arms; UPDATE accounts SET balance=balance before preflight/timing (180s setup-only socket timeout). Untimed diagnostics check the same full logical digest through the unchanged runner before freezing. Same logical values and fresh plans/counters on both sides; whole heap all_visible == 0 before and after. Five measured alternating paired rounds of 15s plus discarded round00. Both range and point median throughput ratios must lie in [.97, 1.02]. The upper guard is prospective: a similarly large apparent gain on the unchanged dirty path cannot validate a small primary gain amid possible arm/host bias. This diagnostic cannot establish complete host stability.

Every phase: median paired peak RSS <= 1.05 and p99 <= 1.10 for both workloads. Range client CPU must stay below 80% of four assigned client cores in every sample; median range server CPU >= 3 cores. CPU/op and throughput under saturation are coupled, not independent measures. Record medians and full ranges, paired ratios, host activity and CPU frequency without claiming exclusive host ownership.

Both engines use CPUs28-31, client32-35; whole harness nice19, checked at runtime. Same cache2048MiB and startup settings except ports and monitor instrumentation. Unchanged frozen final-client/bench SHA9f5b0222 is used for both. No profilers overlap timing. Prior baseline profile: fetched ancestry about4.72% range and0.22% point, overlapping truncated samples, a scale only rather than an expected gain or a strict upper bound. A much larger apparent improvement demands explanation before acceptance.

Source acceptance remains separate: full cargo build/clippy, workspace tests (pg-engine covered by the frozen full-crate run plus the strengthened full-wire rerun; remaining workspace tested after performance), all-target pg-engine Clippy, fresh pnpm test:pg --force and candidate regression comparison to retained baseline. Regression acceptance must find the baseline-comparison section with zero newly differing units and independently compare results.tsv, requiring identical full file/unit coverage and release profiles on both sides. Known baseline failures cannot be counted as passes or silently waived. Keep source review, test failures and skipped gates visible. No accepted improvement until these checks and independent result/trail review complete.

Conservative risks: the unswapped dirty upper guard can reject a neutral change from slot bias; passing both primary blocks may require a true gain larger than 2% plus slot bias. Rejection alone does not prove no effect or a regression. Swapping does not remove binary layout differences or drift between blocks.
